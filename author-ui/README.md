# Sensible Studio author UI

The Sensible Studio page editor. It works like AEM's: the page is rendered by Sensible Studio in a frame (`wcmmode=edit`), an overlay
outlines its components, and every change is a Sling POST, so content stays byte-compatible with AEM. Component
dialogs are a project's real `cq:dialog`s, including everything they inherit from Core Components, saved the way AEM saves them.

```
src/
├── granite/        @sensible-studio/granite-ui: the Granite dialog library (no editor code, reusable)
├── start/          the Start screen (/studio/start.html): navigation tiles and tools (navigation.ts)
├── sites/          the Sites console (/sites.html/<path>): views, Create Page wizard, Move
├── security/       users, groups and permissions (/security/*.html)
├── tags/           the Tags console (/tags.html/content/cq:tags)
├── shell/          the product bar shared by the consoles
└── editor/
    ├── App.tsx     the editor: page, modes, selection, clipboard, actions
    ├── api/        StudioClient (what the editor needs from Sensible Studio) and its HTTP implementation
    ├── model/      editables read from the page (data-studio-* attributes), layout grid helpers
    ├── overlay/    overlay over the frame: hover, selection, toolbar, drop targets, move, column resize
    ├── shell/      top bar, side panel rail, emulator
    ├── panels/     Assets, Components, Content Tree
    ├── dialogs/    component dialog / page properties window, Insert New Component
    └── testing/    in-memory Sling POST emulator and demo content for the Granite tests
fixtures/           real WKND dialogs (generated by studio-adapter) for the tests
scripts/package.mjs builds the studio-editor content package
```

## Run

```bash
npm install
npm run dev        # http://localhost:5173/editor.html/content/wknd/us/en.html, against Sensible Studio on :4502
npm test           # vitest: editables model, every WKND dialog renders and round-trips, EL, Sling POST
npm run package    # dist-package/studio-editor-<version>.zip: install it on Sensible Studio and open :4502/editor.html/...
```

The dev server serves the editor at `/editor.html/<page>.html` (the AEM URL) and proxies everything else to Sensible Studio
(`STUDIO_TARGET`, default `http://localhost:4502`). That includes content, clientlibs, DAM renditions and the short URLs
the resource resolver mapping produces (`/wknd/us/en/...`). It adds Basic auth (`STUDIO_AUTH`, `admin:admin` by default,
dev only) and rewrites `Origin`/`Referer` so Sling's referrer filter accepts the POSTs.

On Sensible Studio itself the `studio-editor` package installs the build under `/libs/studio/editor/app`, and `EditorPageServlet`
(`studio-cq-impl`) answers `/editor.html/*` with it. Anonymous visitors go to the Sling login form first.

Server side the editor needs `studio-cq-impl` (edit-mode decoration, `/bin/studio/editor`) and `studio-adapter`
(`/bin/studio/dialog`).

## Start

`/studio/start.html` (also `/` in dev) is the entry point, laid out like AEM's start screen. It has a product bar with
the signed-in user and Sign Out, and a rail with two tabs:
- **Navigation:** the tiles. Sites and Experience Fragments open the list of their pages; a page (or XF
  variation) opens in the editor. Assets opens the repository browser at `/content/dam` for now. Content Fragments
  and Projects are not built yet.
- **Tools:** categories (General, Deployment, Operations, Security, About) with the Sling and Composum consoles:
  repository browser, packages, bundles, OSGi configuration and installer, jobs, health checks, and the Sensible Studio
  security consoles (Users, Groups, Permissions).

Tiles and tools are plain data in `src/start/navigation.ts`. The page lists come from
`/bin/studio/editor.json?op=pages&root=&depth=&xf=`. The editor's Page Information menu has **Go to Start**.

## Sites

`/sites.html/<path>` (Start → Sites) browses pages and folders below `/content` like AEM's Sites console:
- **Views:** Column (one column per level, preview with thumbnail and metadata), List and Card. The choice is
  remembered in the browser.
- **Title menu:** jumps to an ancestor. Header: **Select All**, **Create → Page**, view switcher, and **Paste**
  after a Copy.
- **Selection** (checkboxes) swaps the header for the action bar:
  - Edit (e), Properties (p), Lock/Unlock, Copy (⌘C), Move (m), Delete (⌫), cleared with Escape;
  - Properties open the page component's dialog full screen;
  - Move renames and/or moves to another parent and rewrites the references to it: in the referring pages you
    keep ticked and always inside the moved subtree;
  - Copy pastes with a free name (`name_1`).
- **Create Page:** two steps, Template then Properties (Title, Name, Page Title, Navigation Title, Subtitle,
  Description, Hide in Navigation). The templates are those of the site's `cq:conf` that are enabled and allowed
  here (`cq:allowedTemplates` on the nearest ancestor, the template's `allowedPaths`/`allowedParents`). The page
  is created from the template's initial content.

- **References:** the column preview lists the pages that refer to the item. Delete lists them too and then asks
  for **Force Delete**. A reference is any string property below `/content` or `/conf` that holds the path as a
  whole path: the path itself, a child, `.html` links, rich text. Found by walking the tree, about 150 ms on WKND.

The data comes from `/bin/studio/sites.json`:
- `op=children`, `op=templates`, `op=references`;
- `POST op=create`, and `POST op=move` with `adjust=<page>` per page to rewrite.

Copy, delete and properties are Sling POSTs. There is no publication or Launches yet; live copies are covered below (MSM).

### Rails

The selector at the left of the header (or the shortcuts) opens a rail beside the view, like AEM's; the choice is
remembered in the browser:
- **Content Only** (`` ` ``): no rail.
- **Content Tree** (alt+1): pages and folders below `/content`, opened down to the current location, loaded level
  by level; a click navigates there.
- **Timeline** (alt+2) of the selected page: created, modified, published, rolled out, its versions, its workflows
  (started, completed steps, completed or terminated), launches, comments and annotations, newest first, with a **Show** filter (Comments,
  Annotations, Activities, Launches, Versions, Workflows; an annotation shows its note in its colour, the component
  it is on and *Open in editor*). Below: a comment field (Enter sends; your own comments can be deleted) and
  **…** → Save as Version, Restore Version, Restore Tree, Start Workflow. A version entry opens to
  **Revert to this Version**, **Preview Version** (the page rendered as it was, in a new tab) and **Compare to
  Current** (full screen: the version and the current page side by side, and the list of changes component by
  component, changed words marked; another version can be picked). Side by side, **Highlight changes** marks the
  changes inside the rendered pages: removed texts and images in red in the version, added ones in green in the
  current page, changed texts outlined with the changed words marked on both sides (`sites/rail/highlight.ts`).
  Closed accordion items and other tabs that hold changes are shown open (dotted outline; the menus stay closed), and
  changes that render nothing (tags, link targets, settings) are counted with a link to the **Changes** tab, where
  they are labelled *Not on the page*. Long texts are compared sentence by sentence first, so the sentences that
  stayed are not marked.
  - **Restore Version** (full screen): the versioned pages inside the page, deleted ones too, each with the version
    to restore and a **Preview Version** button (a deleted page too, so it can be looked at first); tick the pages
    and Restore. A deleted page comes back from its version; a page deleted outside Sites that Sensible Studio kept (even one
    that never had a version) offers the version *As deleted*, the page as it was.
  - **Restore Tree** (full screen): a date, **Preserve Non Versioned Pages**, and the revised structure — what
    happens to each page (restored to a version, back from deletion, kept, or deleted when not preserved).
  - Deleting in the console (or through a Sling POST delete) saves a version of every page inside first, so both can
    bring it back. Pages deleted otherwise (CRX, WebDAV, JCR) are found by their earlier versions.
- **References** (alt+3): the pages that refer to the selection and, for one page, its live copy status and the
  launches that hold a copy of it (each opens that copy in the editor).
- **Site** (alt+4): the site of the selection or location — pages, live copy and locked pages, the latest change,
  the `cq:conf`, the language roots and the templates of the configuration.
- **Filter** (alt+5): full text, path, template, tags, modified date, live copy and locked pages. While a filter is
  set the view shows the matching pages as a list (select them for the action bar) with a **CSV Report**.
  **Saved Searches** at the top: **Save Search** keeps the current filters under a name (per user, in the
  repository, so they follow you to another browser); choosing one sets its filters, the bin deletes it.

The rails read `/bin/studio/siterail.json` (bundle `studio-siterail`); the tree and the references use `/bin/studio/sites.json`.
Code: `src/sites/rail/`.

## MSM (live copies)

`src/msm` is the Multi Site Manager UI. It talks to `/bin/studio/msm.json` (`MsmClient`). The content it writes is the
same as AEM's (`cq:LiveSyncConfig`, `cq:LiveRelationship`, `cq:LiveSyncCancelled`, `cq:propertyInheritanceCancelled`),
so live copies move between AEM and Sensible Studio unchanged.

- **Sites:**
  - live copy pages carry a chain badge in all three views;
  - the column preview shows the live copy (source, status, last rollout, rollout configs, own values) with
    Synchronize, Reset, Suspend / Resume and Detach, or, for a blueprint, its live copies with Rollout and the Live
    Copy Overview;
  - the action bar has **Rollout** and **Live Copy Overview** for a blueprint page and **Synchronize** for a live copy
    page;
  - **Create → Live Copy**: source page, title, name, sub pages or not, rollout configs.
  - **Create → Site**: a blueprint configuration (or a new one from any site root, saved only together with the
    site), then the languages and chapters to start with, title, name, owner and Live Copy (unchecked by default, as in
    AEM; plain copies without it). Same structure as AEM's Create Site;
  - the column preview lists the page's **Versions** with Restore (rollouts with "Standard rollout with versions"
    save one before they change the page).
- **Editor:**
  - inherited components (`data-studio-msm="inherited"`) are read-only: no Configure, Cut, Delete or move; the toolbar
    has a closed lock (**Cancel inheritance**);
  - cancelled components get an open lock (**Re-enable inheritance**, which synchronizes them again);
  - the Page Information menu has **Live Copy Status** (or **Blueprint**) and **Synchronize Page**.
- **Page properties:** fields that rollouts update show a chain and are read-only. Breaking the chain cancels the
  inheritance of that property (or of the whole child node for fields with `cq-msm-lockable`); closing it re-enables
  and resynchronizes it. Inherited fields are not posted on save. Properties rollouts never touch (by default every
  `jcr:` property and most `cq:` and `sling:` ones, like AEM) have no chain. `@sensible-studio/granite-ui` exposes this as
  `GraniteForm`'s `inheritance` prop (`InheritanceModel`).

## Security

Start → Tools → Security opens three consoles, with tabs to switch between them:
- **Users** (`/security/users.html`): name, login, status, job title and email, with a filter and a switch for
  system users. Selecting rows gives Properties (p), Permissions, Disable/Enable and Delete. `admin`, `anonymous`
  and system users cannot be deleted.
- **Groups** (`/security/groups.html`): the same table for groups.
- **User / group properties** (`/security/user.html?id=`, `/security/group.html?id=`, no `id` to create): Details
  (profile under `profile/`, password on create, Change Password, Account enabled), Groups (member of), and
  Members for a group or Impersonators for a user. Nothing is written before **Save & Close**.
- **Permissions** (`/security/permissions.html?principal=`): pick a user, a group or Everyone and see its access
  control entries on every path. **Add ACE** / edit takes a path, Allow or Deny, privileges (the common ones, or
  all of them) and an optional `rep:glob`; an edited entry keeps its place in the list. **Check Permissions**
  shows what the principal may do at a path, counting its groups and `everyone`.

Server side this is `/bin/studio/security.json` in the `studio-security` bundle: the Jackrabbit user manager and
access control manager, under the signed-in user's session, so only someone allowed to manage users and ACLs can
change anything.

## Tags

`/tags.html/content/cq:tags/...` (Start → Tools → Tagging) is the Tags console, after AEM's:
- **Views:** Column (namespaces and tags level by level, details of the selected tag with the pages and assets
  that use it) and List.
- **Create → Create Tag / Create Namespace:** Title, Name (derived from the title until edited), Description, Tag
  Path (with a tag picker).
- **Selection:** Create Tag (below the selected one), Edit (p), Move (m), Merge, Delete (⌫), cleared with Escape.
  - Edit: title, description and titles per language (`jcr:title.<lang>`, languages from `languages` on
    `/content/cq:tags`).
  - Move renames and/or moves the tag; Merge gives the content tagged with it the target tag, moves its sub-tags
    below the target and deletes it. Both rewrite the `cq:tags` values of the pages and assets that used the tag or
    its sub-tags, so nothing is left pointing at a tag that is gone.
  - Delete lists what uses the tags and then asks for **Force Delete**; the tags are removed from that content.

Server side this is `/bin/studio/tags.json` in the `studio-tagging` bundle (tag IDs as in AEM: `ns:a/b`, the `default`
namespace when there is none, tag paths accepted too). There is no publication.

## Workflow models

`/workflow/models.html` (Start → Tools → Workflow → Models; the bar below the header switches between Models, Instances, Launchers and Inbox) lists the workflow models, after AEM's console:
- **Views:** List (Title, Description, Details with the runtime version, Synced, Type: Default / Custom / Not
  Editable for runtime models without a design) and Card.
- **Create → Add Workflow Model:** Title and Name (derived from the title). The model is created under
  `/conf/global/settings/workflow/models/<name>` and synced right away.
- **Selection:** Edit (e), Start Workflow (Run Workflow: payload picked with the same repository picker as the
  dialogs, title, comment), Delete for custom models.

`/editor.html/conf/global/settings/workflow/models/<name>.html` is the model editor:
- The flow from Flow Start to Flow End; OR and AND splits show their branches side by side.
- The side panel lists the steps (Participant, Dynamic Participant, Process, OR Split, AND Split, Goto). Drag one
  onto the flow, double-click it to append it, or click a "Drag steps here" placeholder and pick one. Existing steps
  are moved by dragging.
- Select a step for its toolbar (Configure, Delete; Enter and ⌫ work too); double-click to configure. Step dialogs
  are ordinary component dialogs (`/libs/cq/workflow/components/model/*` from `studio-workflow-content`), so they
  render with the Granite renderer. Their selects get options from datasources registered in
  `src/workflow/registry.ts`: registered processes and participant choosers, users and groups, the model's steps
  (Goto target).
- **Sync** writes the runtime model (`/var/workflow/models/<name>`) that new workflows start with; the bar shows the
  version and whether there are changes not synced yet. Model Properties edits title and description.

`/workflow/instances.html` (Tools → Workflow → Instances) lists workflows in three views:
- **Running:** running and suspended workflows, with their current step and its assignee.
- **Failures:** workflows with a failed step, and why it failed.
- **Archive:** completed and terminated workflows.

Selection actions there: Open History (every step with assignee, who completed it, times and comments), Suspend /
Resume, Retry Step (failed steps), Terminate, and Delete (ended workflows only).

`/workflow/inbox.html` lists the active steps assigned to the signed-in user or to one of their groups (the `admin`
user also counts as `administrators`):
- **Complete:** where the workflow branches, the Next Step offers the OR split's branches, with the default branch
  preselected. A comment is optional.
- **Delegate:** gives the step to another user or group.
- **Open Payload** and **Workflow History**.

`/workflow/launchers.html` lists the launchers: path regular expression, event type (Created, Modified, Removed),
node type, conditions, workflow, enabled, exclude list and run modes.
- **Create** and **Properties** open the same form.
- **Enable**, **Disable** and **Delete** work on custom launchers; those shipped below /libs are read-only.

Default models (below /libs) open read-only in the model editor; **Edit** copies one to /conf/global, and the copy
replaces it.

**Start Workflow** in the Sites console (pages) and in the Assets console (assets) asks for a synced model, a
title and a comment, and starts one workflow per selected item.

The bell in the product bar of every console shows how many steps wait in the inbox and opens it. It refreshes every
minute, and right away after a workflow starts or a step is completed or delegated.

Workflow features available in the model editor:
- **Model Properties** has **Transient Workflow**: the instance is removed a minute after it ends.
- **Participant steps** have a **Timeout** (Off, Immediate, 1h, 6h, 12h, 24h) and a **Timeout Handler** (Auto
  Advancer: an overdue step is completed along its default route). The Inbox shows when a step is due.
- **The OR split dialog** shows only as many Branch tabs as the split has branches. A behaviour rule hides a Granite
  tab panel together with its tab.

**Stages:**
- Model Properties lists the stages of a model, in order (add, rename, reorder, remove; saved as
  `cq:workflowStages`).
- Each step can be given one in the Workflow Stage field of its dialog, and the editor tags the step with it.
- Instances, Inbox and the workflow history show the stage a workflow is in, e.g. "Approval (2 of 3)".

**Start Workflow in the page editor:** the Page Information menu has it too, with the page as payload.

**Process step timeouts:** process steps with Handler Advance off get Timeout and Timeout Handler like participant
steps. A process that does not complete its step in time is moved on along the default route.

**Purge Settings:** in Workflow Instances → Archive.
- Shows how many workflows have ended, the oldest one and the last housekeeping run.
- Sets after how many days ended workflows are removed, or keeps them.
- **Purge Now** removes workflows that ended more than a chosen number of days ago.
- Administrators only.

Server side this is `/bin/studio/workflow.json` in the `studio-workflow` bundle.

### How the editor knows the page

With `wcmmode=edit`, Sensible Studio writes the editor's metadata on each component decoration of the page being edited.
Components of other pages, such as experience fragments, get none:

```html
<div class="title aem-GridColumn aem-GridColumn--default--12"
     data-studio-path="/content/wknd/us/en/jcr:content/root/container/title"
     data-studio-type="wknd/components/title" data-studio-title="Title" data-studio-dialog="true">…</div>
```

Containers also get `data-studio-container`, their grid `data-studio-grid`, and an empty slot with `data-studio-placeholder`.
Components that take dropped assets get `data-studio-drop` and `data-studio-drop-accept`. `model/editables.ts` turns
this markup into a tree.

`GET /bin/studio/editor.json?op=page&path=<page>` adds what the markup cannot carry:
- the page info and the template's breakpoints;
- per container, the component types its policy allows and the `assetToComponentMapping` (e.g. `image/*` → Image);
- the info for each of those components.

`op=assets` searches the DAM for the Assets panel.

Writes are plain Sling POSTs:
- create: `container/*` with `:nameHint` and `:order`;
- move and copy: `:operation=move|copy` with `:dest` and `:order`;
- delete: `:operation=delete`;
- layout: `cq:responsive/<bp>/width|offset|behavior`;
- dialogs: the Granite form entries.

After each change the frame re-renders in place, keeping the scroll position and the selection.

## How a dialog gets on screen

1. **Server** (`studio-adapter`, `DialogTreeResolver`): walks `sling:resourceSuperType`, merges `/apps` over `/libs`,
   merges the dialogs of the chain with the Sling Resource Merger rules (`sling:hideResource`, `hideChildren`,
   `hideProperties`, `orderBefore`) and expands static `include`s. Returns the raw resource tree as JSON.
   Nothing is flattened: tabs, columns, wells, includes are all still there.
2. **Prepare** (`granite/prepare.ts`): evaluates `${...}` expressions (`granite:hide`, `checked`, `value`) against
   the component policy (`cqDesign`), collects show/hide controllers, applies the field rules that replace the
   editor client libraries listed in `extraClientlibs`.
3. **Render** (`granite/render.tsx`): every node is rendered by the component registered for its
   `sling:resourceType`, after `granite:hide` and `granite:rendercondition`. Unknown types are shown as such,
   never silently turned into a text field.
4. **Submit** (`granite/form`): each mounted field contributes Sling POST entries the way Granite does —
   `@Delete` for unchecked checkboxes, `uncheckedValue`, `@TypeHint` for typed values and `String[]`,
   composite multifields as `item0..n` child nodes.

### Looks and editor client libraries

Fields are laid out like Coral: the label above the field, its help (`fieldDescription`) as an (i) icon with a
tooltip at the end of the label row, checkbox help next to the checkbox. The behaviour AEM's editor client libraries
add is re-expressed as rules in `builtins.ts` (`registerBehavior`):

- **Image v3 / Teaser v2** (`core.wcm.components.image.v3.editor`): "Inherit featured image from page" shows the page
  image instead of the asset field; the alt text comes from the page image, from the asset's `dc:description`
  (shown greyed in the field) or is typed in; content with its own asset and no flag opens with the flag off.
- **Image v2, Teaser v1/v2**: alt / title / description fields disabled while inherited.
- **Embed** (`core.wcm.components.embed.v1.editor`): only the fields of the chosen type (URL, embeddable, HTML).

The **children editor** posts what AEM's does: `./<item>/cq:panelTitle` per item, `./<item>/sling:resourceType`
for an added one (named `item_<timestamp>`), `itemOrder` and `deletedItems`. Sling's POST servlet ignores the last
two; `ContainerItemsFilter` (`studio-cq-impl`) applies them once the POST succeeded.

## Extending

```ts
import { createDefaultRegistry } from './granite';

const registry = createDefaultRegistry()
  // a project widget, same contract as Sling: resource type -> renderer
  .registerComponent('myproject/dialog/widgets/colorpicker', MyColorPicker)
  // options for a select's datasource
  .registerDataSource('core/wcm/components/commons/datasources/allowedheadingelements/v1', async () => [...])
  // what an editor clientlib did in AEM, as field rules
  .registerBehavior('myproject.components.hero.editor', {
    disable: [{ field: './title', when: [{ field: './titleFromPage', is: true }] }],
  });
```

A field component uses `useField(name, initial, { entries, validate })` and renders inside `FieldShell`;
see `granite/components/fields/text.tsx` for the smallest examples.

## Page properties and Style System

Core Components dialogs include the standard page fields (`wcm/foundation/components/basicpage`) and the Style
System tab (`cq/gui/components/authoring/dialog/style/...`) by path. On AEM that is product content; Sensible Studio ships its
own clean-room versions: page properties in `../studio-uberjar/studio-compat-content/studio-wcm-foundation`, the Style System
in `../studio-authoring-content`. The dialog endpoint also
returns the instance's content policy (`path` parameter), which feeds `${cqDesign...}` and the Styles tab.

## Template editor

`/editor.html/conf/<site>/settings/wcm/templates/<t>/structure.html` (and `.../initial.html`) opens the editable
template editor, laid out like AEM's (`editor/template/`, server side `TemplateEditorServlet` at `/bin/studio/templates`):

- **Modes:** Structure, Initial Content and Layout (Layout works on the structure). Pages made from the template show
  its locked structure; unlocked (orange) containers are where authors add content.
- **Structure:** each component gets Policy and Lock/Unlock in its toolbar; an unlocked container shows its
  *Allowed Components* with a policy button per component (the policy of that component inside the container).
- **Initial Content:** only unlocked containers can be edited; an unlocked container the initial content has no node
  for yet is rendered from the structure and created on the first insert, paste or move.
- **Policies:** full-screen dialog like AEM's: choose, add or duplicate a policy, title and description, the other
  templates sharing it, and the component's design dialog on the right. Done assigns the policy (mapping under
  `policies/jcr:content/...`) and saves its properties. The container design dialog has Allowed Components (groups as
  `group:<name>`), Default Components (asset to component mappings) and Responsive Settings.
- **Page menu:** Initial Page Properties (the page properties of `initial`), Page Policy, Enable/Disable Template.
  Enabled and disabled templates show AEM's warning banner.

### Templates console

*Tools > General > Templates* (`/libs/wcm/core/content/sites/templates.html/conf[/<c>]`, `src/templates/`, server side
`TemplatesConsoleServlet` at `/bin/studio/templateconsole`): the configurations under `/conf`, then the templates of one as
cards or a list, with their thumbnail, template type and status.

- **Create** (`createtemplatewizard.html/conf/<c>`): pick a template type (the configuration's, `/conf/global`'s,
  `/apps/settings`' or `/libs/settings`', by `ranking`), then title and description. The type's structure, initial
  content, policies and thumbnail are copied into a new draft template; *Open* goes to the template editor.
- **Selection actions:** Open, Properties, Enable, Disable, Copy (a draft `<name>-copy`) and Delete, which is refused
  while pages use the template (the dialog lists them).
- **Properties** (`/mnt/overlay/wcm/core/content/sites/templates/properties.html?item=<template>`): Basic (title,
  description, status, type, path) and Thumbnail (upload an image or clear it; applied on Save).
- Publish/Unpublish are not offered: Sensible Studio has no publish tier yet. AEM's *Generate Preview* of the thumbnail is not
  implemented.

## Known gaps

- Datasources implemented in Java inside Core Components need `com.adobe.granite.ui.components.ds` services in Sensible Studio;
  selects that depend on them keep their stored value.
- Template types are not created from the UI (as in AEM, developers add them under `settings/wcm/template-types`).
- No undo/redo, annotations, Timewarp or Developer mode.
- In-place (inline) rich text editing is not implemented; text is edited in the dialog.
